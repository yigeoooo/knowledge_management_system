# 多轮知识库对话架构与实现

日期：2026-11-09。版本：第三版及实施说明。状态：已实现，接口以 [机器人会话接入](robot-conversation-api.md) 为准。

实现说明：桌面端保留固定系统菜单，右侧为可收起的历史会话和聊天区。删除发起者记录在 AuditLog 中；上下文范围和摘要版本放在每轮的 `context_snapshot` 中。近期历史默认 6 轮，历史 JSON 使用 9000 个 UTF-8 字节作为保守 token 预算，单轮最多更新一次摘要；超预算或摘要失败均显示上下文遗漏提示。当前后台支持归属对象、标题/问题和删除状态筛选，时间范围控件尚未提供。机器人身份沿用序列号识别，本轮未引入设备密钥认证。

已确认：管理员先选择用户，再查看该用户的多段连续对话；用户删除采用软删除；机器人创建时绑定一个知识库，支持修改绑定，提问不传知识库编码；机器人不带会话 ID 的首问创建新会话，携带会话 ID 时继续该会话；记忆只在单个会话内有效。换绑后旧会话只读，网页采用异步响应及轮询，机器人采用单次 HTTP 请求等待最终答案；模型接入使用 LangChain，固定问答流程使用 LangGraph。

## 1. 用户体验与范围

- 问答页改为左侧历史会话、右侧消息流和底部输入框。支持新建、打开、继续和删除自己的会话。
- 历史按最后提问时间倒序，游标分页；消息按轮次顺序展示，较早消息按需加载。刷新或重新登录后可恢复。
- 点击“新对话”进入空白状态；首次发送时创建会话和首轮问题，避免空会话堆积。会话创建使用独立幂等键。
- 首问生成截断标题，不额外调用模型；首问前显示现有推荐问题。
- 每个会话创建时固定一个知识库，不可切换；选择其他知识库时开启新会话。
- 页面 URL 使用 `/qa?conversation_id=...`，保留现有 `/qa` 动态页面权限匹配方式。
- 管理员问答历史采用“用户列表 → 该用户的会话列表 → 会话完整消息流”三级浏览。选择用户是主导航，不只是平铺日志表上的可选筛选项。另提供机器人标签，按“机器人 → 会话 → 完整消息流”浏览。
- 选择具体会话后可导出 Word 文档，包含整段历史（不受消息分页限制）、会话归属、知识库、时间、逐轮问答与引用资料。已软删除及已关闭会话可按审计权限导出；进行中轮次明确标记当前状态，导出不触发新问答。
- 导出中的“引用资料”使用二级标题并设置默认折叠，支持该功能的 Word 桌面版可按需展开。折叠范围仅包含本轮引用，下一轮问答正常显示；不支持折叠的阅读器仍可显示完整内容。
- 首版采用“正在回答”提示，完成证据审阅后展示完整答案；不将未审阅的模型草稿逐字推送。流式进度可后续加入。
- 首版不做跨会话记忆、编辑旧消息后分叉、成功回答重新生成。失败轮次支持重试。
- 机器人创建和编辑表单增加必选知识库，机器人问答从服务端绑定读取目标知识库。一个知识库可以绑定多台机器人，一台机器人当前绑定一个知识库。
- 机器人提供两个提问入口：不带 `conversation_id` 时原子创建会话并提交首问；带 ID 时向该会话提交新问题。首问响应即返回会话 ID，无需先调用单独的空会话创建接口。
- 所有新提问都携带独立 `request_id`；它只负责超时重试去重。判断是否新会话的字段是 `conversation_id`，不能混用这两类 ID。

## 2. 数据模型

新增 `qa_conversations`，已有 `qa_logs` 继续作为一轮问答的唯一存储，不同时维护另一套重复的消息表。

```text
User  ─┐
       ├── QAConversation 1 ── N QALog（一次用户提问及其回答）
Robot ─┘         │                       │
       二选一归属 └── KnowledgeBase       └── sources 证据快照
```

`qa_conversations` 主要字段：

| 字段 | 用途 |
|---|---|
| id / source_type / user_id / robot_id | 会话标识及 WEB/ROBOT 归属，用户和机器人二选一 |
| knowledge_base_id | 创建时固定的知识库 |
| robot_binding_version | ROBOT 会话创建时绑定版本的快照，WEB 为空 |
| title / created_at / last_message_at | 列表展示和排序 |
| creation_request_id | 同一用户或机器人范围内唯一，首次创建幂等 |
| next_turn_no | 在行锁事务内分配顺序 |
| deleted_at / deleted_by_user_id / deleted_by_robot_id | 软删除时间及发起者 |
| closed_at / closed_reason | 会话只读原因，如机器人换绑；关闭与软删除分开 |
| memory_summary / summary_through_turn_no | 较早对话摘要及其覆盖位置 |
| memory_version | 防止异步摘要覆盖新版本 |

扩展 `qa_logs`：

- `conversation_id` 迁移阶段可空，正常 WEB/ROBOT 记录回填后均归属会话；新写入强制关联。无法确认归属的异常旧记录隔离为管理员可见迁移例外。
- `turn_no`：会话内轮次，唯一约束 `(conversation_id, turn_no)`。
- `resolved_question`：结合历史解释后的独立检索问题，保留原始 `question`。
- `answer_kind`：区分知识回答和澄清请求；执行成功不等于已经回答知识问题。
- `context_through_turn_no` / `context_summary_version`：记录实际使用的历史范围。
- `lease_token` / `lease_expires_at` / `attempts`：后台执行租约及重试控制。
- 保留现有问题、答案、来源、状态、耗时、模型和全局唯一 `request_id`。
- 新增 `PENDING`、`CANCELLED` 状态；更新所有状态过滤、统计及前端映射。

数据库 CHECK 约束：WEB 会话要求 `user_id` 非空、`robot_id` 为空，ROBOT 反之。分别设置 `(user_id, creation_request_id)` 和 `(robot_id, creation_request_id)` 部分唯一索引。用户列表索引按 `(user_id, deleted_at, last_message_at, id)`，机器人使用对应的 `robot_id` 索引；消息索引按 `(conversation_id, turn_no)`。

已有 `qa_logs` 中来源、用户、机器人及知识库字段为兼容旧统计暂保留，新写入只能从所属会话派生，不接受客户端任意组合。会话所有者和知识库不可修改。业务入口和迁移检查这组关联一致性。

管理员选定用户后，再按知识库、时间范围、标题或问题内容查询其会话，结果按会话去重。机器人会话使用相同规则。会话和首问在同一事务内创建，首问校验或入队失败则一起回滚，不产生空会话。

这里一轮包含一问一答足以满足当前交互；如以后加入工具调用、分支或多角色消息，再迁移到独立消息模型。

## 2.1 机器人绑定与换绑

`robots` 新增 `knowledge_base_id` 外键及单调递增的 `binding_version`。新建机器人必须选择一个启用知识库；更新其他字段时可不传绑定字段，显式传空值不代表解绑。机器人列表和详情展示当前绑定知识库；列表支持按知识库筛选。知识库改名或改 code 不影响 UUID 关联，也不触发换绑。

机器人会话保存创建时的知识库 ID 和绑定版本。历史会话的知识库不能随 `robots.knowledge_base_id` 改变，否则旧记忆会混入新库且审计归属失真。

建议换绑规则：

1. 管理员将机器人从 A 换绑到 B 时，校验 B 启用、锁定机器人行，更新绑定并递增版本，记录前后知识库及操作者。
2. 同一事务将该机器人的原开放会话标记只读（`closed_reason=knowledge_base_changed`），取消未完成问答并使执行租约失效。历史答案和来源保留，管理员仍可查看。
3. 机器人之后不带会话 ID 提问，自动在 B 创建新会话；若继续携带旧 ID，返回明确的 `409 CONVERSATION_BINDING_CHANGED`，客户端清除当前 ID 后，用新的 request_id 发起新对话。不自动将原问题改投 B 或移植 A 的记忆。
4. 机器人从 A 换到 B 再换回 A，旧版本会话仍只读。不能仅比较知识库 ID 相等就恢复旧会话；绑定版本避免这种情况。
5. 新建会话、继续提问、领取任务和写回答案都校验绑定；事务统一按“机器人 → 会话 → 问答轮次”顺序加锁。换绑与答案提交互斥，长模型调用不持锁；换绑先提交时旧任务不能写回。
6. 结果查询同样检查会话状态与绑定版本，避免换绑后机器人继续播报旧库结果；管理员历史详情仍可读。绑定失效时返回可处理的业务错误，不悄悄新建会话。

目标知识库停用或归档时，拒绝新问答且阻止未完成答案写回；不自动寻找其他知识库。这里不增加知识库物理删除级联，原有历史保留。恢复原知识库启用且未发生换绑时，可继续原本未关闭的会话。

有 `/robots` 页面权限的管理员应能获取“可绑定知识库”选项，无需额外获得知识库管理权限。建议新增 `/robots/knowledge-base-options`，只返回绑定所需的启用知识库 ID、名称及编码。历史已绑定但现已停用的知识库仍显示其名称和状态，不能假装它未绑定。

## 3. 上下文记忆与检索

```text
本轮问题 + 服务端历史（近期原文 + 更早摘要）
    → 消解“它、刚才那步、继续”等指代，生成独立检索问题
    → 现有混合检索、相邻片段和章节扩展
    → 基于当前有效资料生成答案
    → 证据审阅
    → 保存本轮结果、更新摘要
```

历史从数据库读取，客户端只提交新问题和会话 ID，不能自行指定其他用户/机器人的历史或伪造 assistant 消息。所有历史选择、摘要读写和上下文缓存均按 `conversation_id` 隔离，不按 `user_id` 或 `robot_id` 聚合记忆；即使属于同一设备，新会话也从空上下文开始。

记忆策略：

1. 保留最近若干完整轮次的原文；建议初始上限 6 轮，同时执行可配置 token 预算。
2. 超出窗口的旧对话形成滚动摘要，记录主题、指代对象、用户约束和未解决问题；摘要带覆盖轮次，原始消息仍完整保存在数据库。
3. 上下文总预算包含系统提示、摘要、近期消息、本轮问题、检索资料及预留输出。按模型限制配置，不沿用无限追加历史的方式。
4. 摘要仅覆盖已完成的连续轮次，摘要与原文窗口按覆盖轮次衔接，避免遗漏或重复。后台更新以版本条件写入；下一轮读取固定上下文快照。摘要失败不使已完成回答失败；保留旧摘要，预算允许时纳入尚未摘要的原文，仍不足时明确较早上下文可能未覆盖。不可无提示地丢掉任意历史并声称拥有完整记忆。
5. 改写问题不得补造事实；“继续”指向不明确时返回澄清问题。改写失败时，仅对可独立理解的问题使用原问题检索，否则请用户明确指代。
6. `FAILED`、`CANCELLED` 轮次不作为成功答案记忆；资料不足的结果保留其状态，不能变成已确认事实。

关键约束：历史回答和摘要用于理解当前问题，不能作为新的知识证据。涉及知识库事实的每轮都重新检索当前可用版本；生成和证据审阅都要收到原问题、改写问题及必要会话语境。文档事实、命令、参数仍必须由本轮真实资料支持。澄清指代或解释对话中用户表达的格式要求可以直接回复，但需标记为澄清/对话管理结果，不能伪装为有文档证据的知识结论。

处理例子：“介绍设备 A 的安装流程”之后问“第二步需要什么？”应定位上一轮第二步所指操作，再检索相应资料；“按刚才三点整理成表格”应保留用户的格式意图，并重新核实三点对应证据。

## 4. 后端模块划分

新增 `application/conversations`，其对外 interface 负责创建、列表、详情、提交问题、重试和删除；所有权、顺序、幂等及生命周期规则集中在这个 module 内。Controller 只做 HTTP 适配。

- `entities/conversation.py`：会话持久化模型。
- `api/conversations/controller.py`：个人会话入口。
- `api/robot_conversations/controller.py`：机器人首问、续问、结果查询及删除入口。
- `application/robots/service.py`：机器人绑定校验、换绑事务、绑定版本及审计；扩展已有创建/编辑逻辑。
- `api/qa_history/controller.py`：管理员只读历史入口。
- `application/conversations/service.py`：事务、归属、幂等、顺序、删除。
- `application/conversations/memory.py`：历史选择、预算、摘要、指代解释。
- `application/qa/answer_service.py`：从现有 `_answer_question` 提取检索及证据审阅编排，网页与机器人共用。
- `application/qa/workflow.py`：有界的对话推理流程，见框架接入评估；隐藏 LangGraph 等实现细节。
- `workers/qa_worker.py`：网页和机器人回答共用后台执行，与文档索引 Worker 分开，避免相互阻塞。

不让前端、Controller 和 Worker 各自维护一套历史拼装或权限逻辑。

## 5. 请求生命周期和并发

网页先持久化、返回 `202`，页面轮询该轮状态。机器人先持久化，再在本次 HTTP 请求内等待最终答案，以 `200` 返回；默认最长等待 180 秒，超时返回 `50401`，客户端复用原 request_id 重发。刷新、关闭页面或切换会话不会丢失已提交问题，也不会取消服务端回答。机器人只播报同一轮已完成且经过审阅的答案，使用 `turn_id` 去重，未完成状态不当成答案。

直接以 `qa_logs` 的待处理状态作为 PostgreSQL 持久任务来源，不复用 `IndexTask`，首版无需 Redis/Celery。网页开发环境可自动唤醒后台执行器，生产使用独立 `qa-worker` 持续扫描。机器人同步入口定向调度自己的轮次，复用同一领取、续租与写回逻辑；等待阶段不持有数据库事务。

1. 验证调用者后查找幂等请求。机器人新对话入口先锁定机器人，读取当前知识库和绑定版本；一次事务完成“会话 + 首轮问答”写入。
2. 相同 request_id、相同调用者和请求内容返回原会话/轮次；两次无 ID 首问的并发重试也只能创建一个会话。相同键不同问题或不同会话返回冲突。换绑后重试旧请求必须仍解析到旧操作并报告绑定失效，不能复用该键在新库创建第二个会话。认证和会话存活校验不得被幂等快路径绕过。
3. 续问短事务锁定会话，检查归属、删除/关闭状态、绑定版本、知识库状态及 `expected_last_turn_no`。该字段是防止多端旧视图提交的可选前置条件：网页携带；机器人可按约定串行发送并只携带会话 ID，若传则严格校验。
4. 同一会话只允许一个待处理/执行中轮次；用数据库部分唯一索引兜底。不同会话可并发。
5. 两个标签页并发发送不同问题时，后到请求返回冲突，要求刷新消息，防止使用错误上下文。
6. Worker 先只读扫描候选任务 ID，再按统一锁顺序使用 `FOR UPDATE SKIP LOCKED` 领取；跳过已锁定的父记录/任务，重新校验待处理状态，不先持有轮次锁再反向锁父记录。模型调用期间释放数据库事务。
7. 长请求续租；完成时按租约令牌、会话存活状态及绑定版本条件写入，过期 Worker 不得覆盖新结果。
8. Worker 重启后扫描过期租约，有限次恢复；外部模型调用可能重复，但业务结果只允许提交一次。
9. 最后一轮失败可复用该轮重试；若已有后续轮次，不允许改写旧失败轮，应重新发送新问题，保持历史顺序稳定。
10. 接收请求、Worker 执行和写回时检查调用者资格：WEB 校验账号及页面权限，ROBOT 校验设备启用状态、凭证及绑定版本；两者均检查知识库及会话状态。停用后不得继续产生可见答案。
11. 当前答案提交前继续校验本轮引用文档版本；执行期间资料已变更时不能提交为当前有效答案。历史读取则使用保存的快照，不要求引用仍是当前版本。

旧 `/web/query` 可在过渡期作为单轮兼容入口。机器人 `/robot/query` 按本版定义升级为“新会话首问”，旧机器人客户端需配合升级：移除 knowledge_base_code，保存会话 ID，并适配响应协议。机器人两个提问入口现均同步等待最终答案，知识库只能由服务端绑定确定，不允许旧 code 绕过绑定选库。

## 6. 接口草案

以下均位于 `/api/v1`：

| 方法及路径 | 行为 |
|---|---|
| `POST /web/conversations` | 幂等创建会话并提交首问，返回会话和首轮状态 |
| `GET /web/conversations?cursor=...` | 当前用户的未删除会话 |
| `GET /web/conversations/{id}` | 会话元数据 |
| `GET /web/conversations/{id}/turns?before=...` | 分页读取历史 |
| `POST /web/conversations/{id}/turns` | 提交问题、request_id、expected_last_turn_no，返回 202 |
| `GET /web/conversations/{id}/turns/{turn_id}` | 查询生成状态及完成结果 |
| `POST /web/conversations/{id}/turns/{turn_id}/retry` | 重试可重试的失败轮 |
| `DELETE /web/conversations/{id}` | 幂等软删除本人会话 |
| `POST /robot/query` | 不接受会话 ID；根据机器人绑定新建会话并提交首问，同步返回会话/轮次 ID、最终答案和 200 |
| `POST /robot/conversations/query` | 必须携带会话 ID，向同一会话提交问题，同步返回轮次、最终答案和 200 |
| `GET /robot/conversations/{id}/turns/{turn_id}` | 读取该设备所属轮次状态与答案 |
| `POST /robot/conversations/{id}/turns/{turn_id}/retry` | 重试最后一个可重试失败轮并同步等待结果 |
| `DELETE /robot/conversations/{id}` | 软删除该设备会话（不是开启新对话的必要步骤） |
| `GET /robots/knowledge-base-options` | 机器人管理页获取可绑定知识库 |
| `GET /admin/qa-users?q=...&cursor=...` | 在历史管理权限下搜索有历史的用户及会话计数 |
| `GET /admin/qa-robots?q=...&cursor=...` | 在历史管理权限下搜索有历史的机器人及会话计数 |
| `GET /admin/qa-conversations?source_type=WEB&user_id=...` | 必选用户，查看其会话 |
| `GET /admin/qa-conversations?source_type=ROBOT&robot_id=...` | 必选机器人，查看其会话 |
| `GET /admin/qa-conversations/{id}` | 会话元数据和归属用户 |
| `GET /admin/qa-conversations/{id}/turns?before=...` | 管理员分页读取整段对话 |
| `GET /admin/qa-conversations/{id}/export` | 按问答日志权限导出完整会话 DOCX；返回文件附件 |

个人接口要求 `/qa` 页面权限且 `user_id == 当前用户`，包含超级管理员的个人聊天入口。越权访问统一返回 404。

管理入口继续使用现有 `/qa-logs` 页面权限，符合当前可授权角色体系；并非所有登录用户可访问。用户/机器人选择接口属于历史模块，不复用要求 `/users` 或 `/robots` 管理权限的维护接口。列表请求按 source_type 要求且仅允许对应的 user_id 或 robot_id。详情仍逐次校验历史管理权限，不依赖页面之前选过用户。

## 6.1 机器人交互协议

按用户提出的两个问答入口落地：一个“不带会话 ID，新建并回答”，一个“带会话 ID，继续回答”。它们调用同一个业务模块，只有会话取得方式不同。也可以未来合为一个可选 conversation_id 的接口，但本版无需同时维护第三种重复入口。

机器人区分两种 ID：`conversation_id` 表示会话，`request_id` 表示一次提问操作；首问同一 request_id 同时标识创建和第一轮。网络重试复用 request_id，新的问题和新的会话使用新的 request_id。建议使用 UUID，避免现有全局请求唯一约束冲突。缺少 request_id 返回 422，不把它解释为开启新会话。

请求正文示例省略通用鉴权头；响应正文沿用 `{code, message, data, request_id}` 包装，以下只展示 `data`。

开启新对话并提问：`POST /api/v1/robot/query`

```json
{
  "serial_no": "robot-001",
  "request_id": "2a480713-6919-4e2b-8f3f-241973c320ab",
  "question": "设备如何启动？"
}
```

后端从 robot-001 当前绑定获取知识库，在同一事务中创建会话和首轮，等待生成完成后返回 HTTP 200（以下为主要字段，完整结构见接入文档）：

```json
{
  "conversation_id": "0956ec0b-e453-4b64-9ce3-fcbd3423d24e",
  "turn_id": "9a48d689-26b8-4b37-ac6a-e77630ab8b51",
  "turn_no": 1,
  "status": "SUCCESS",
  "answer": "依据资料生成的最终回答"
}
```

后续提问：`POST /api/v1/robot/conversations/query`。上一轮结束后继续发送：

```json
{
  "serial_no": "robot-001",
  "conversation_id": "0956ec0b-e453-4b64-9ce3-fcbd3423d24e",
  "request_id": "f1a578c0-3ee9-4bb5-a34d-72bb8678c8a8",
  "question": "刚才第二步需要注意什么？"
}
```

```json
{
  "conversation_id": "0956ec0b-e453-4b64-9ce3-fcbd3423d24e",
  "turn_id": "c7dbda71-bdf6-4c5b-964a-cd5d109192eb",
  "turn_no": 2,
  "status": "SUCCESS",
  "answer": "依据资料生成的最终回答"
}
```

同一次机器人请求等待完成后返回 `status`、适合播报的 `answer` 和 `answer_status`。内部保存与网页相同的证据和结果状态，管理端可展开引用。需要更严格的多端顺序保护时可额外携带 expected_last_turn_no，示例第二问应为 1。该轮若失败，读取错误后明确重试或发送新问题，不能仅因 HTTP 超时创建新轮次。

两个问答入口都不接受客户端传 knowledge_base_code/knowledge_base_id：首问使用当前绑定，续问核对会话固定知识库和绑定版本。错误知识库字段返回 422，避免让客户端误以为字段生效。

续问入口的 ID 必须有效、属于当前设备、未删除、未关闭且绑定版本匹配。空值/格式错误返回 422，不存在或属于其他设备返回 404，换绑关闭返回 409；都不自动降级为新会话。用户要求“只要有 ID 就携带记忆”在满足这些资格后成立。

建议由机器人应用在新交互、用户要求重新开始或操作者切换时清除当前 conversation_id，下次走首问入口。若增加无操作超时，也由客户端明确开启新会话。设备重启后，只有确认仍是同一交互时才恢复本地保存的会话 ID；多人共用机器人时不要把上一位操作者的会话自动交给下一位。管理员换绑则通过旧会话 409 响应告知客户端重新开始。

每次请求均校验当前机器人归属，不能只凭会话 ID 访问。现有实现只有 `serial_no` 校验，序列号可由调用方自行填写；严格的设备隔离建议为新协议增加每设备 API 凭证（服务端保存哈希并支持轮换），让凭证解析出 robot_id，再与序列号/会话归属比对。如果暂沿用序列号机制，归属检查能阻止误用其他设备 ID，但不能防止冒用其他设备序列号；需在实施前确定是否一并升级。

## 7. 删除、历史证据与管理员视图

用户已确认软删除。会话及所有轮次保留在数据库，通过父会话的 deleted_at 统一阻止个人访问，管理员仍可查看并标记“用户已删除”；不需要逐轮复制删除标记。机器人删除遵循相同规则。页面确认提示应明确该语义。保留期限或永久清除如有要求，再增加独立策略。

- 删除后个人列表、详情、续问及重试均不可访问；其他标签页应回到新对话。
- 正在生成时删除，将未完成轮次标为取消，写回检查阻止回答重新出现。已经发出的外部模型请求不保证立即停止。
- 管理员为只读审计视图，不以用户身份继续对话；沿用每轮引用内容快照。
- 读取历史不能沿用 `_log_response` 中“所有引用必须仍是当前版本”的限制，否则更新文档会导致旧会话打不开。
- 将“历史展示”和“新回答有效性校验”分离：旧问答文本和来源快照始终可读；原文件仍存在且允许访问时临时生成预览 URL，否则标记文件已失效。前端不长期保存预签名地址。
- 管理员先在用户列表中选择某个用户，再看到其会话标题、知识库、轮数、最近提问时间和删除状态；选择一个会话才展示连续消息。切换用户时清空上一位用户的会话详情及未完成请求。支持已停用/已删除用户的历史，不能因为账号当前不可登录就丢掉审计记录。
- 用户列表提供“会话数”和“提问轮数”，分别统计，空会话不计入有效历史。默认会话历史包含软删除记录并有明确标记，可按删除状态筛选；仪表盘提问次数仍按轮统计。
- 机器人标签同样先选设备再看会话，不把设备历史展示为某个用户的会话，也不把多位操作者的不同会话合并。
- 机器人历史显示会话创建时知识库；可同时显示设备当前绑定，但二者不能混淆。换绑关闭会话标记“已换绑，只读”，与“已删除”区分。

7. 部署新后端及 Worker，完成存量机器人绑定和客户端协议升级，再开放机器人问答并切换网页。复用 `/robot/query` 时其入参和响应均发生变化，必须协调切换，不能声称对旧设备透明兼容。启用多轮写入后，不能直接回滚成只理解单轮的旧页面；故障时优先关闭新提交并保持历史只读。

## 10. 验收重点

- 用户 A 无法读取、续问、删除或轮询用户 B 的会话；有历史管理权限的角色可只读查看。
- 机器人 A 无法使用机器人 B 的会话；同一设备可以新建多个完全隔离的会话；无会话 ID 的首问超时/并发重试只生成同一会话和首轮。
- 机器人创建必须绑定知识库，只有机器人管理权限也能选库；修改绑定生效，机器人无法通过请求参数改用其他库。
- A→B 换绑后旧会话拒绝续问，A→B→A 后旧会话仍不恢复；新问题只检索当前绑定，新记忆为空。
- 换绑与首问/续问/答案写回并发时，绑定版本和锁顺序有效；旧任务不能在换绑后提交答案，结果轮询不会交付已失效旧库答案。
- 不存在、无效、其他设备或软删除的 conversation_id 不会悄悄创建新会话；缺少 request_id 不能冒充新对话请求。
- 管理员选用户 A 只显示 A 的各段历史，选 B 后无串页；有历史权限但没有用户管理权限的角色也能使用历史用户选择器。
- 新对话不携带旧对话记忆；再次打开历史可正确解释指代、继续步骤及改变输出格式。
- 长对话摘要覆盖顺序正确、预算受控；用户指令与历史答案不会取代文档证据。
- 页面刷新、网络超时、重复提交、两个标签页、Worker 崩溃和过期租约不会生成重复轮次或覆盖新结果。
- 删除进行中的会话不会复活；管理员仍按选定删除政策查看。
- 原文更新/归档后历史可读，新问题只用当前有效资料。
- 旧 WEB/ROBOT 记录数量和归属迁移前后相符；旧机器人原知识库不被新绑定覆盖；新协议支持首问建会话、连续追问、查询状态和恢复超时结果。
- pytest 覆盖业务入口与故障路径；PostgreSQL 集成测试验证锁、部分唯一索引和租约；Playwright 验证用户完整会话流程和管理员详情。SQLite 测试不能替代并发验证。

## 11. LangChain / LangGraph 接入建议

推荐方向：会话、权限、日志、软删除及任务生命周期继续由 Flask + SQLAlchemy 管理；使用 LangChain 统一模型调用和结构化结果，用 LangGraph 表达固定的问答流程。具体能力核对与官方来源见 [框架评估](./langchain-conversation-evaluation.md)。

```text
网页 / 机器人
    → Flask 鉴权与会话入口
    → SQLAlchemy 会话、轮次及任务状态
    → QA Worker
    → LangGraph：载入上下文 → 理解追问 → 检索 → 生成 → 审阅 → 有限修正
                         └→ 不明确时返回澄清
    → 按租约提交最终结果 → 更新会话摘要
```

建议职责分工：

| 部分 | 使用方式 |
|---|---|
| 模型调用 | LangChain 的 DeepSeek 集成，封装在现有 AI adapter 后；验证 JSON 和 schema 能力，不假定模型支持所有结构化方法 |
| 追问解释、答案生成、证据审阅 | 有类型的输入输出，明确节点与预算；保留现有 evidence_ids 校验、无证据回退及最多一次修正 |
| 条件分支及有限修正 | LangGraph 显式 StateGraph，固定路径和终止条件，无需开放式自主 agent |
| 文档检索 | 复用现有 pgvector + 关键词 + 相邻切片/章节逻辑，作为图节点；无需改成另一套向量表 |
| 历史和记忆 | 业务数据库读取会话轮次和摘要，组装为图输入；每次仅传当前会话 |
| 对话展示、软删除、权限 | 项目业务模块负责，框架不代替 |
| 待处理队列、并发锁、租约 | PostgreSQL + Worker 负责，图执行不代替任务调度 |

首版图按“一轮问答”执行，输入明确的会话上下文快照。先不启用持久 checkpointer，进程中断后用同一 turn_id 和租约重跑该轮，避免立即增加一套需要与业务日志同步的持久历史。图只返回推理结果，不直接写入业务表；Worker 负责条件提交。

若后续模型调用成本或恢复时延需要逐节点续跑，再引入 PostgreSQL checkpointer：检查点只用于执行恢复，业务轮次仍是用户历史的唯一来源；以服务端派生的 turn_id 标识本轮执行 thread，与客户端 conversation_id 做显式映射。不能把下一轮误当作上一轮恢复；删除、账号停用及过期租约都必须阻止检查点继续写回。旧检查点保留策略另行定义。摘要仍以当前会话业务记录为准。

不使用跨会话 Store。官方所谓 short-term/thread memory 必须映射到本项目的单会话需求，不能按 user_id 或 robot_id 创建全局共享历史。LangChain 的自动摘要能力可作为工具参考；当前是固定 RAG 流程，摘要的覆盖轮次、权限及版本写入仍需项目控制，不必为了使用 agent middleware 改造成 agent。

引入成本包括版本锁定、provider 特性兼容、更多框架类型及回归验证。它能使流程分支和模型适配更清晰，但不会自动解决归属、软删除、幂等或幻觉。现有功能也可以继续用 Python 函数实现；选择框架的理由是后续维护与流程扩展，不是会话记忆本身做不到。

框架本身不保证更快或减少 token：追问解释和摘要都会增加调用。首问无需指代改写；摘要达到预算阈值后才更新；模型 adapter 自动重试、图修正和 Worker 恢复共同受总次数及总时限约束，不能每层独立无限重试。网页和机器人分别记录排队、检索、生成与审阅耗时，以实际结果调整体验。

实施时先做小范围技术验证：当前 DeepSeek endpoint 的 JSON/schema 行为、超时/异常映射、检索结果不变、证据审阅与重试上限保持一致。通过后锁定版本再纳入正式实现。此草案没有安装依赖或改动运行中的问答逻辑。

## 12. 本版建议审核项
