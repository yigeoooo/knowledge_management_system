# 提示词管理与质量评测

管理员菜单新增“提示词管理”和“质量评测”，普通用户默认不可访问。已有登录页未显示菜单时刷新或重新登录。

## 提示词存在哪里

正式提示词保存在 PostgreSQL：

| 表 | 内容 |
| --- | --- |
| `prompt_templates` | 用途、展示名称、当前发布版本、发布代数 |
| `prompt_versions` | 不可变正文、版本号、修改说明、创建人和时间 |
| `qa_logs.prompt_snapshot` | 本轮执行时固定的完整提示词版本与正文 |
| `evaluation_datasets` | 每个知识库唯一的评测集 |
| `evaluation_examples` | 问题、参考标注、修订号、启用确认人和时间 |
| `evaluation_runs` | 固定实验条件、逐题基线和候选结果、人工复核、执行租约 |

用途包括网页回答、机器人回答、证据审阅、推荐问题及其审阅、会话摘要、网页与机器人追问理解。LangChain 负责组织调用，LangGraph 编排流程；LangSmith 记录执行及版本元数据，PostgreSQL 是发布版本的权威来源。不会在每次调用时从云端拉取提示词。

`app/resources/prompts-v1.json` 是初始化兼容模板；迁移使用冻结副本 `migrations/data/prompts-v1.json`，`init.sql` 也包含相同初始版本。日常修改通过管理页面写入数据库，编辑模板文件不会覆盖已发布内容。结构化输出 schema、证据校验、权限、机器人纯文本整理仍由程序负责。

## 修改、试测、发布与回退

1. 在“提示词管理”选择用途，基于现有版本编辑正文并填写修改说明。
2. “保存新版本”只新增不可变版本，不影响正式问答。
3. 选择发布验收使用的知识库评测集；“试测此版本”带着版本和所选评测集进入“质量评测”。其余用途保持当前发布版本；也可以同时选择多个用途的候选版本。
4. 选择固定测试集开始对比。后台对每题分别执行基线与候选，轮换先后顺序，不改变线上发布状态。
5. 看逐题答案、证据文档、状态、耗时与 token，再进行人工复核。候选答案全部复核合格后，回到提示词页面检查发布条件。
6. 回退时选择历史版本，先用当前基线完成评测与人工复核，再重新发布。发布采用代数检查，其他管理员已经发布时要求刷新，避免覆盖别人的操作。

发布由后端强制校验，直接请求发布接口也不能绕过。必须满足：

- 实验使用已启用且标注完整的测试题，全部题目执行成功，且每题候选答案经人工复核合格。
- 实验属于所选知识库的唯一评测集，且实验题目 ID 集合与该集当前全部已启用题目完全相同。新增或启用题目后必须重新评测；草稿不参与正式验收。
- 实验确实覆盖所选用途，候选版本 ID 与待发布版本一致。草稿试测和单纯“已完成”不代表通过。
- 实验基线仍为当前发布组合；用于单用途发布的实验一次只修改一个用途，其他用途保持当前发布版本。多用途组合实验可用于探索，不能直接作为单用途发布依据。
- 测试题的修订、启用状态、知识库索引和运行配置仍与评测时相符；变化后需重测。历史版本回退同样适用。

页面显示未满足的原因、关联实验和刷新入口。只有一个有效知识库评测集时自动选择；有多个知识库时必须选择本次验收使用的知识库，不会借用其他知识库的合格实验。提示词仍然全局共用，发布后对所有知识库生效；本次验收只校验所选知识库的唯一评测集，不要求其他知识库的评测集全部通过。发布请求携带 `evaluation_run_id` 和 `dataset_id`，服务端重新核对并将实验编号、测试集与环境指纹记入发布审计。自动字面指标供分析，语义和事实是否合格由逐题人工复核确认，不把简单关键词分数当作质量验收。

后续开始执行的问答使用新版本；进行中的轮次和崩溃重试复用已经保存的快照，单轮不混用版本。追踪中的提示词指纹和版本映射可用于定位变更。发布不会重新生成历史答案，也不会改变已保存的历史摘要；测试摘要提示词请使用专门的摘要样本。

正文是系统指令文本，材料由服务端单独传入，不支持模板中执行代码或任意工具。按用途保留对相应 JSON 输出与事实依据的要求；机器人回答仍需简洁纯文本。调整格式不能绕过服务端结构校验。

## 人工标注怎么做

“人工标注”是维护者按原始资料填写并确认预期结果，不是把某次模型答案直接当标准答案。

1. 每个知识库只能建立一个评测集，后续直接在该集中维护题目，支持反复运行多次实验。前端禁用已有评测集的知识库，后端校验并由数据库唯一约束防止并发重复创建。建议包含高频事实、数字与条件、跨段比较、多轮指代、资料不足、机器人简洁表达等类型。
2. 每题填写从所属知识库搜索、多选预期文档、必需事实要点、预期状态；参考答案用于人工对照，核对依据写清章节或 Excel 行号。没有可靠标准的项目留空。
3. 答案要点尽量拆成可核对的事实，如价格、计价单位、适用范围，不要求复述完整原句。自动要点指标是字面检查，同义表达可能低分，必须人工复核。
4. 对照原文核查后点击“保存并启用”，一次完成保存和启用，可直接用于正式评测。未完成时点击“保存草稿”。修改后保存会增加题目修订号，旧评测不能用于证明新版题目的效果。
5. 默认只用已启用样本。可选择包含草稿试测，但结果明显标记为“草稿试测 · 非验收结论”。

初次导入的“江源杯问答回归集（待人工审核）”包含来自两份旅游攻略和套票 Excel 的 8 道草稿题。历史实验与当前题目状态以页面为准；草稿试测仅用于验证流程，不代表质量验收通过。

预期文档实际保存 `expected_document_ids`，标题仅为展示快照；召回和引用指标按文档 ID 匹配，文档改名或重名不会误判。下拉框只加载所属知识库，可搜索更多结果，以文件名和编号区分同名文档；已删除、其他知识库或未索引文档在保存、启用和开始评测时都会被拒绝。

升级会把已有标题标注在同一知识库内唯一匹配为文档 ID。无法匹配或重名的标注不会猜测，撤销其原审核并提示重新选择。旧实验报告保持原始快照；由于计分方式已更新，旧报告不作为本次升级后的发布依据，需要重测。

注意：两份攻略有重复事实，同一问题可能有多个合法引用文档。出题时应按实际评价目标补全预期文档，不要把合法替代依据误判成错误。资料本身的笔误或相互矛盾需要先人工确认。

## 对照资料出题

出题窗口左侧编辑题目，右侧搜索、切换并预览所属知识库文档。Word 保留标题和表格排版，Excel 使用只读表格，可切换工作表、滚动查看并临时放大；PDF、图片、视频及文本使用相应预览方式。不支持在线预览的格式可下载原文件。

切换预览不会改动题目或预期文档。需要作为评测依据时点击“加入预期文档”；放大后点击“返回对照”，已填写的内容保留。小屏幕通过“题目编辑 / 资料预览”切换。文档获取接口限定本评测集知识库，不授予文档修改权限。

普通知识问答不再显示历史语境区。只有选择“连续追问”或“会话摘要”时，才显示按轮次填写问题、回答及可选旧摘要的表单，无需手写 JSON。

连续追问和摘要题支持“从问答日志导入”。先按当前回答渠道选择用户或机器人，再选择本知识库的会话。右侧完整展示每轮问题和回答，可在问答卡片上选择起点、终点；点击“预览待导入问答”后再次核对所选内容，确认后写入题目。会话和轮次均支持分页，最多选取连续 30 轮。保存时仍适用历史内容长度限制，超限会要求缩小范围，不会静默截断答案。

导入只复制所选范围内已完成且有回答的问答，失败、取消、未完成和空回答会跳过。资料不足、部分回答、资料指引以及澄清回答仍可作为真实上下文。导入会替换当前历史问答并清空旧摘要，测试问题、预期文档和参考答案保留；导入后可编辑，点击保存才持久化。历史原始回答并不等于正确参考答案，仍需对照知识库资料标注。

连续追问应选择测试问题之前的轮次，不能把待测问题的回答或之后的问答加入上下文。导入不读取会话的最新摘要，避免包含选择范围之后的信息。题目保存独立的问答副本和来源会话、轮次 ID，后续原会话变化或软删除不会改变已有样本。

导入同时要求质量评测与问答日志查看权限，接口再次校验知识库、渠道及会话删除状态；已软删除的会话不会出现在导入列表中。该功能不增加数据库字段，沿用测试题 inputs.context JSON；不用修改 init.sql 结构。

出题窗口在大屏使用更大的宽高，资料预览约占 55% 宽度；左右独立滚动，仍可单独放大资料。小屏保留题目编辑和资料预览切换。

本次不增加数据库字段，沿用 `reviewed_by/reviewed_at` 记录保存并启用的确认人及时间；接口返回 `status=draft|enabled`。旧的已审核题目自然显示为已启用，未确认草稿不自动启用。API 创建和编辑时显式传入 `status`；省略时默认草稿，避免导入题目误入正式评测。旧 `/review` 接口仅保留兼容，当前页面不再使用。题目启用与评测答案人工复核是不同操作，提示词发布仍要求候选答案逐题复核合格。

## 任务类型与上下文

- **知识问答**：单轮问题，运行完整检索、重排、生成和核验流程；选择网页或机器人渠道。
- **连续追问**：填写当前追问，以及此前每轮的问题和回答，用于检验指代理解。可补充更早的对话摘要；不会读取别的会话。
- **会话摘要**：使用和正式会话压缩相同的摘要操作。输入固定的 `turns` 和可选旧 `summary`，用要点、禁止内容和人工复核检验讨论对象、限制和未解决事项是否保留。不写入真实会话。
- **推荐问题**：把测试问题作为检索主题，使用推荐与审阅提示词生成问题。检查问题能否由资料回答、是否重复，并标注人工结论。

如果选中的候选用途没有相应任务或渠道样本，服务端拒绝开始实验，避免“没有执行该提示词却显示测试通过”。单次最多 100 题，同时排队/执行任务数有限制。摘要历史输入限制为 18000 UTF-8 字节。

## 单独测试一道题

在“测试题与人工标注”的题目操作列点击“单题测试”，确认题目并选择候选提示词版本，然后点击“开始单题测试”。草稿和已启用题目都支持，使用该题当前已保存的内容；编辑中的内容需要先保存。版本选择仅展示这道题实际使用的提示词用途，例如摘要题只展示会话摘要提示词，连续追问会展示相应渠道的追问理解提示词。未指定的用途使用当前发布版本。

后台只为所选这一题生成基线与候选两组输出，复用进度条、逐题对比和人工确认功能。结果保存在“实验记录”，标记为“单题测试”；关闭详情后回到题目列表，方便继续调整。单题结果用于调试，即使人工确认合格、评测集恰好只有一道题，也不能直接作为发布依据；正式发布仍需在“发起版本对比”中运行该集全部已启用题目并通过验收。

接口沿用 `POST /api/v1/evaluations/runs`，增加可选的单题选择参数：

```json
{
  "dataset_id": "评测集 UUID",
  "example_id": "所选测试题 UUID",
  "expected_revision": 1,
  "name": "单题测试 · 套票价格",
  "overrides": {"answer_robot": "候选提示词版本 UUID"}
}
```

指定 `example_id` 时必须携带当前题目修订号，服务端检查题目属于所选评测集；已修改返回 409，不存在或不属于本集返回 404。单题模式允许草稿，服务端固定 `reviewed_only=false`，快照及响应记录 `scope=single`。省略单题参数则保持原来的完整评测行为，`scope=dataset`；旧实验默认视为完整评测。仅所选题目及版本会被冻结，不会执行其他题目，也不会把多次单题结果拼成完整验收。

沿用 `evaluation_runs.snapshot` JSON 保存运行范围，不增加数据库字段，无需新增迁移或调整 `init.sql`。

## 优化前后怎样比较

每次实验固定测试题、标注、启用状态、全部提示词正文和版本、文档当前索引版本及其更新时间、模型与检索配置。编辑测试集或发布其他版本不会改变旧实验。执行过程中索引、知识库状态或配置改变时中止本次对比，不混合不一致条件。

对比详情使用居中宽弹窗：左边选择题目，右边并列展示基线和候选，顶部可展开汇总指标和实验条件；支持导出完整 JSON。删除题目不删除旧实验里的快照。

版本选择只作用于**候选**：例如当前机器人回答发布 v2、选择历史 v1 时，左侧基线执行 v2，右侧候选执行 v1。两侧答案卡片直接标明本题使用的提示词用途和版本，可展开查看固定的正文；“本次固定的提示词版本”列出两组完整配置。基线固定于原实验发起时，后续发布不会改变旧实验；候选并不一定比基线更新。

执行异常的实验支持在**当前记录内**补测：顶部“一键重测所有异常题”处理所有异常或未生成的题目，左侧每道异常题的“重新测试这道题”只处理选中题目。实验 ID、名称和类型不变，不新建记录。正常题目的答案和人工确认结果保留；同一道异常题中已成功的一侧答案也保留，例如只有基线失败时只重测基线。补测成功后，该题需人工确认。

接口为 `POST /api/v1/evaluations/runs/{id}/retry`：空请求或 `{}` 表示重测全部异常题，`{"example_id": "原实验中测试题的 UUID"}` 表示只重测该题。沿用原实验固定的基线、候选提示词正文、题目、参考标注和历史上下文，不接受覆盖版本或题目。返回 `202` 和更新后的同一条记录；排队或执行期间再次请求返回 `409`，正常题目不允许重测。服务中断恢复时保留已保存的重测结果，继续执行尚未完成的部分。

知识库须有效，索引和运行配置须与原实验快照一致；条件变化返回 `409`，需重新发起版本对比，避免把不同条件下的结果混入同一实验。发布验收仍核对当前发布版本、启用题目和运行条件，重测不能绕过验收条件。

待重测的两侧标识保存在现有 `evaluation_runs.results` JSON 的 `retry_pending` 数组中，完成后保留空数组供任务恢复识别；审计日志保存重测题目及原异常类型、追踪编号。无数据库结构变更，无需调整 `init.sql`。新的模型调用失败会保存安全的中文原因和追踪编号；较早的异常记录仅保存异常类型时仍显示 `ChatError` 等原始类型，不推测历史失败原因。

“实验记录”分为“评测集记录”和“单题测试记录”，分别查看当前评测集对应类型的最近 50 条记录。列表同时展示答案生成进度和人工处理情况：待处理、部分已处理、全部已处理，以及已确认题数和合格情况。逐题确认合格或不合格都计入已处理；全部已处理不代表全部合格或满足发布条件。保存人工确认后列表同步更新，执行异常和空实验不会因为生成结束或进度为 0/0 被标记为全部已处理。

待处理记录不显示合格、不合格数量；部分已处理和全部已处理记录也仅在存在不合格题目时，显示绿色“合格 N 题”和红色“不合格 N 题”标签。没有不合格题目时仅保留处理状态与已确认题数。数量由后端按已保存的候选答案人工结论逐题统计；未确认或执行失败的题目不会算作不合格。对比详情左侧每道题使用醒目的状态标签：合格为绿色、不合格为红色，待确认或执行异常为橙色，等待生成或未生成为灰色。修改并保存人工结论后，标签与列表数量同步更新。数量为实时计算字段，无需修改数据库结构。

列表接口 `GET /api/v1/evaluations/runs` 支持 `dataset_id` 和 `scope=dataset|single` 筛选，先筛选再取最近 50 条；不传筛选参数仍兼容原来的列表调用。旧实验没有 `scope` 时归入评测集记录。

有历史语境的题目在详情中默认展开“本次评测的历史上下文”，显示本次实验固定的摘要、每轮问题和回答，并支持折叠。无历史时明确显示按单轮问题评测。单题测试的发起窗口也可预览已保存的历史。后续编辑题目或删除原始会话，不会修改旧实验的输入快照。

单题与完整版本对比都使用题目保存的 `inputs.context`，各题、基线和候选独立执行，不会把上一道测试题的回答作为下一题历史。追问理解、生成和审阅都收到该历史；生成与审阅还将当前问题、改写后的问题、此前用户提问和摘要组成明确的问题输入，避免仅依赖改写而遗漏人数、预算等用户条件。历史助手回答仍保留在会话语境里，不能替代当前知识库证据。此调整不修改数据库中的提示词正文或自动发布版本。

新实验的两组答案分别显示“结合历史理解的问题”，用于检查改写是否遗漏条件；旧实验未保存此字段时只展示当时已冻结的历史。用户人数等条件可以来自历史，但老人、儿童票价等业务规则仍须有资料依据；按统一单价计算时应明确是估算，不能捏造优惠规则。

此次模型输入方式变化更新了运行条件版本 `rag-v2-prompts-v3-conversation-input`。旧实验结果继续保留；用于新版本发布时需重新完成评测，防止把旧流程的验收结果用于新流程。

自动指标有文档 Recall/Precision@10、MRR、回答状态准确率、要点字面覆盖率、引用文档准确率和禁止内容避让率。没有对应标注就不计算该指标。失败调用单独计数，不伪装成质量得分；各均值显示样本数，差值只计算双方都成功的同题结果。

人工复核每题只选择一次“本题对比结果：合格 / 不合格”，判断所选试测版本（候选）答案是否满足要求；基线答案保留供对照，无需再单独评分。复核说明选填，便于记录错误、遗漏或改善点。建议检查事实与数字、遗漏条件、无依据推断、引用、是否答非所问、机器人表达长度。人工合格率按已确认题目的候选结论计算，未确认题目不计入分母；发布仍要求全部题目已确认且候选答案全部合格。

实验列表和对比详情展示真实执行进度：已完成题数 / 总题数及百分比，每题的两组答案生成并保存后更新，页面约每 4 秒自动刷新。等待执行、生成中、生成完成和执行异常分别展示；100% 仅表示题目执行进度，不代表人工验收通过。详情同时显示已人工确认题数。关闭详情或离开页面不取消后台实验，重新打开可继续查看。

人工复核接口 `POST /api/v1/evaluations/runs/{run_id}/reviews/{example_id}` 请求示例：`{"candidate": 1, "note": ""}`，其中 `candidate` 必填整数 `1`（合格）或 `0`（不合格），`note` 可省略。返回更新后的完整实验详情；旧客户端的 `baseline` 评分仍兼容，已有历史评分保留，新记录不生成基线评分。沿用 `evaluation_runs.results` JSON，无数据库结构变更，不需要新增迁移或调整 `init.sql`。

优化时优先一次只改一个因素，用同一批已启用问题复测，检查改善题和退步题。模型有随机性，即使提示词相同两次答案也可能不同；小样本单轮差值不能证明稳定改善。另保留一批不用于调整提示词的验收题，避免只适配开发测试集。

若要比较不同检索/切片策略，保存调整前实验，更新策略并重建索引后，用同一测试集再运行并导出报告对比；当前页面自动成对比较的是同一运行条件下的提示词版本，不会自动部署另一套检索配置。

## LangSmith 与部署

正式问答与评测继续使用已配置的 LangSmith；新评测运行的元数据包含 `evaluation_run_id`、`evaluation_example_id`、`evaluation_arm`，逐题结果保留运行编号。是否上传输入输出由现有 `LANGSMITH_CAPTURE_CONTENT` 控制。页面中的本地实验、人工标注与分数保存在 PostgreSQL，并不自动同步成 LangSmith Dataset / Experiment；需要云端数据集实验可继续使用 `rag-evaluate --publish` CLI 显式上传。

升级：

```bash
cd knowledge_back
uv sync --locked
uv run flask --app app db upgrade
# 重启后端及现有问答、索引 Worker
# 生产环境增加常驻评测 Worker
uv run flask --app app evaluation-worker
```

迁移版本为 `e42b6c8d901a`（在文档 ID 标注迁移之后新增知识库评测集唯一约束）。若旧库存在重复评测集，保留题目最多的一份（同数量时保留较早创建的），合并其他集合的题目和实验；同名题目自动加后缀，原实验快照、结果和人工复核保持原样，合并来源记入审计日志。题目合并后若旧实验未覆盖当前全部已启用题目，则需重新评测。迁移合并保留全部题目；单次实验仍最多 100 题，超出时先将暂不参与验收的题目改为草稿。全新部署执行根目录 `init.sql`，会创建上述表、初始提示词和管理员菜单。默认 `EVALUATION_WORKER_AUTOSTART=true`，创建或查看任务时唤醒进程内 Worker；生产环境建议关闭并运行独立 Worker，以便服务重启后自动恢复待执行任务。评测每题成对保存进度，租约过期可恢复，已完成题不会重复执行；中断在一对答案中间时该对可能重算并产生额外模型费用，最多尝试 3 次。
